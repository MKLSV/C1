## 2. Компоненты бэкенда (модули)

| Модуль | Ответственность |
|--------|-----------------|
| **Turn handler** (`/api/turn`) | оркестрация одного хода диалога |
| **Context builder** | сборка промпта: system + история(усечение) + профиль + каталог |
| **LLM client** | вызов Claude API, prompt caching, ретраи, парсинг JSON |
| **Profile merger** | слияние `profile_patch` в `sessions.profile` |
| **Matcher** | скоринг каталога + диверсификация (matching-algorithm.md) |
| **Catalog service** | запросы к `occupations` и связям |
| **Report builder** | финальный отчёт из `recommendations` |
| **Safety filter** | детектор кризиса до показа ответа |
| **Privacy/consent** | согласие, удаление данных |

## 3. Поток данных «один ход» (детально)

1. `POST /api/turn { session_id, message }`.
2. Загрузить `sessions.profile` + последние N `messages`.
3. Если прошлый ход просил каталог → выполнить Matcher, подготовить вставку.
4. Context builder → запрос в Claude API.
5. LLM возвращает JSON `{ reply, stage, profile_patch, ready_to_finalize,
   needs_catalog_query }`; валидация (ретрай при сбое).
6. Safety filter по `reply`/`message`; при кризисе — заменить ответ.
7. Profile merger: deltas суммируются, массивы дополняются, constraints/context
   перезаписываются.
8. Сохранить `messages` (user+assistant), обновить `sessions`.
9. Если `ready_to_finalize` → Report builder → запись `recommendations`.
10. Вернуть `reply` (+ отчёт на финале).

**Важно:** LLM stateless — полный `profile` передаётся каждый ход; история реплик
усекается/суммируется, профиль — нет.

## 4. Модель состояния

- Источник истины — `sessions.profile` (JSONB), см. dialogue-script.md.
- Идемпотентность хода: защита от двойных сабмитов (один message → один ход).
- Возобновление: по `session_id` восстанавливаем профиль и историю.

---

## 5. Стоимость и производительность

- **Драйвер стоимости — токены LLM.** Снижаем:
  - prompt caching системного промпта и каталога;
  - суммаризация ранней истории длинных сессий;
  - Opus 4.8 на «думающих» ходах (гипотезы/финал), Sonnet 4.6 на простых.
- Следить за **ценой одной сессии**; заложить лимит ходов/сессий на пользователя.
- Кэш каталога в памяти/edge (он меняется редко).

---

## 6. Безопасность данных

- TLS in-transit, шифрование at-rest (Supabase).
- Минимизация ПДн в запросах к LLM (без лишних идентификаторов).
- LLM-провайдер: данные API не используются для обучения (подтвердить настройку).
- RLS (Row Level Security) в Supabase: пользователь видит только свои сессии.
- Секреты (API-ключи) — только на сервере/в env, не на фронте.

| Вопрос | Рекомендация | Альтернатива |

## 8. Окружения

- `dev` (локально/превью Vercel) → `staging` → `prod`.
- Миграции БД версионируются (`migrations/`), применяются по порядку.
- Секреты разделены по окружениям.

# Схема БД: каталог профессий + профиль пользователя

> Хранилище для платформы профориентации. Цель — описать **конкретные**
> профессии/занятия (включая самозанятость) так, чтобы AI мог матчить их с
> профилем пользователя, объяснять «почему» и подавать данные о доходе/входе.
>
> СУБД: **PostgreSQL** (готово под Supabase). DDL — в
> [`migrations/0001_init.sql`](../migrations/0001_init.sql).

---

## Принципы модели

1. **Профессия = конкретная роль**, а не направление. Не «инженер», а «инженер
   по контролю качества на пищевом производстве». Поле `granularity` помогает
   отличать широкие категории от конкретных ролей.
2. **Теги вместо одного теста.** Каждая профессия размечена по RIASEC, типу
   Климова, навыкам, ценностям, формату занятости — чтобы матчить с профилем
   с разных сторон.
3. **Наём и своё дело равноправны.** `employment_modes` хранит, доступна ли роль
   как наём, фриланс, своё дело.
4. **Данные о деньгах и входе — структурированы**, чтобы бот не выдумывал.
5. **Связь с открытыми таксономиями** (O*NET, ESCO) через внешние коды —
   на будущее для импорта и масштабирования.

## Сущности (обзор)

| Таблица | Назначение |
|---------|-----------|

## Ключевые поля `occupations`

- `title` — конкретное название роли.
- `granularity` — `field` | `occupation` | `specialization` (мы целимся в два
  последних).
- `riasec_code` — напр. `SAE` (первые 1–3 доминирующих типа).
- `riasec_scores` — JSONB `{R,I,A,S,E,C}` 0–100 для точного матчинга.
- `klimov_type` — `tech|human|sign|art|nature`.
- `big_five_fit` — JSONB: какие черты помогают/мешают (для отсева).
- `employment_modes` — массив `employee|freelance|business|hybrid`.
- `work_context` — `remote|office|hands|with_people|solo|team` (массив).
- `day_in_life` — короткое «день из жизни» для подачи примером.
- `demand_level` — `low|medium|high` (для «проверки реальностью»).
- `onet_code`, `esco_uri` — связь с внешними таксономиями.

`income_profiles` вынесены отдельно, т.к. у одной роли доход разный в найме и в
своём деле (зарплата vs за проект vs подписка vs продукт).

## Логика матчинга (профиль → каталог)

Скоринг гипотезы для пользователя (псевдо):

```
score(occupation, profile) =
    w1 * riasec_similarity(profile.riasec, occ.riasec_scores)      // косинус
  + w2 * skills_overlap(profile.skills, occ.skills, transferable)  // в т.ч. база
  + w3 * format_match(profile.constraints.format, occ.work_context, occ.employment_modes)
  + w4 * income_fit(profile.constraints.income_*, occ.income_profiles)
  + w5 * values_overlap(profile.values, occ.values)
  - penalty(big_five_conflict(profile.big_five_signals, occ.big_five_fit))
```

- Навыки дают **бонус, а не фильтр** (прошлый опыт — плюс, но не обязателен):
  отсутствие навыка не исключает роль, если есть короткий `entry_path`.
- Для разнообразия в выдаче берём топ по score, но с разными
  `employment_modes` (наём / своё дело / гибрид) — как в сценарии, этап 4.

## Заполнение каталога

- **Старт:** импорт топ-профессий из **O*NET** (задачи, навыки, смежные роли) +
  ручная локализация под рынок РФ/СНГ, добавление вариантов самозанятости
  (фриланс/ремесло/контент), которых в гос-классификаторах мало.
- **Доход/спрос:** из hh.ru (зарплаты, вакансии, навыки), Avito Услуги (спрос на
  самозанятость), фриланс-бирж (Upwork/Fiverr) — складываем в `income_profiles`
  и `demand_level`.
- **Навыки:** общий справочник `skills` можно засеять из ESCO (многоязычный) или
  O*NET, чтобы один навык связывал много профессий (важно для транс­ферности).

## Замечания по эксплуатации

- `riasec_scores`, `big_five_fit`, `user_profile` — JSONB: гибко на этапе MVP,
  можно нормализовать позже.
- Для быстрого матчинга по RIASEC — GIN-индекс на JSONB и/или отдельные
  числовые колонки + индекс.
- `sessions.profile` — единый источник состояния диалога (см. сценарий).
- При росте каталога вынести полнотекстовый поиск по `occupations.title`/
  `day_in_life` (pg_trgm) для подсказок.
